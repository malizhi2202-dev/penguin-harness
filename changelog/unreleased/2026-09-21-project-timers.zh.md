# 对齐定时器：按计划把项目的仓库对齐

- **日期：** 2026-09-21
- **类型：** feature
- **范围：** `core`、`server`、`web`、`docs`

[English](2026-09-21-project-timers.md)

项目现在可以声明 `timers.toml`，定时器会按节律把项目下的本地仓库对齐到上游、检查文档与代码的一致性，
并在被要求时把发现的问题交给 Agent 处理。右侧栏新增「对齐定时器」面板：定时器列表、下次与上次运行、
每个仓库的最近一份报告、文件本身的编辑器，以及运行历史。遍历的仓库就是该项目各工作区所在的仓库，
与代码仓库面板所见一致；没有仓库列表可配置。

一次运行按固定顺序做三件事：`commit = "auto"` 时先提交工作区，提交信息由 diff 生成；然后 fetch，
并以 fast-forward（`sync = "merge"` 时为 merge）把各分支对齐到上游；最后报告漂移——代码变了而没有任何
文档变、文档变了而没有代码变、改动的文档里相对链接或代码段路径指向不存在的目标（`file:line`），
以及尚未落到上游的本地提交。先提交是刻意的：否则"绝不合并脏工作区"会让合并这一步在 Agent 编辑过的
工作区里永远不会发生。

## 细节

- 文件位于 `<projectDir>/timers.toml`，一个 `[[timer]]` 一个任务，可手工编辑。`enabled` 缺省
  `false`、`sync` 缺省 `fetch`、`commit` 缺省 `off`、`docs` 缺省 `true`，所以写到一半的条目不会
  产生任何影响。`period` 形如 `30m` / `12h` / `7d`，下限 5 分钟；省略即为一次性。
- 调度完全复用 Agent 定时任务的模型：懂了其中一个的人不该再学第二套。文件是意图、永不回写，运行状态
  存在 SQLite；server 第一次看到某个定时器时已经过去的触发时刻只被消费、不会被补跑；无论成功与否该时刻
  都会被消费，因此失败会被如实上报而不会陷入重试循环；删掉条目即删掉它的状态与历史。
- git 操作走代码仓库面板同一套经过校验的服务：只用 `execFile` 传 argv、每个值都校验、
  `GIT_TERMINAL_PROMPT=0`、逐命令超时。新增的原语是 fast-forward 或 merge（冲突即中止）、工作区暂存
  与提交，以及"存在未完成操作则跳过"的守卫。
- 两张表 `project_timer_state` 与 `project_timer_runs` 作为迁移 5 引入（swap-safe，带 `down`）。
  进程异常退出时留下的未结束运行，会在启动时被改标为 `interrupted`，而不是一直显示为"运行中"。
- 路由位于 `/api/projects/:projectId/timers/`：任何成员可读，只有 owner 可写、可手动运行。完全无法
  解析的文件会被拒绝；只有一个坏条目的文件会被保存，并在响应中返回该条目的错误——一个笔误不该让另外
  九个定时器一起存不下去。
- 交接是语义的那一半：当定时器设置了 `agent_prompt` 且本次运行发现值得处理的问题时，报告会变成
  Session 里的一条 Prompt——默认使用项目内置 Agent，也可绑定既有 `session_id`。绑定的 Session 正忙时
  这一轮跳过交接，而不是无限排队；下一次运行会报告同样的发现。
- 已知边界一并写明，而不是留给日后发现：这里不与任何托管平台通信，因此不感知 pull request、review 或
  CI，"尚未落地的提交"是它在本地对应的概念；检查基于模式，含义上悄悄与代码脱节的文档不会被发现；
  引用检查只能证明路径存在，不能证明它周围的文字仍然成立。
