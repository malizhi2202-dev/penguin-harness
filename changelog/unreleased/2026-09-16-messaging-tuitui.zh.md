# 消息通道新增第五个渠道：推推（Tuitui）

- **Date:** 2026-09-16
- **Type:** feature
- **Scope:** `server`, `web`, `docs`

[English](2026-09-16-messaging-tuitui.md)

360 的企业 IM 推推（Tuitui）作为第五个渠道加入了消息通道，与飞书、Telegram、QQ、微信并列。
绑定推推机器人的 Session 会应答它的私聊、群聊与团队帖子，接收文本、图片与文件，也能把文本与文件发回去，
所用的绑定 API 与编辑器与其他四个渠道相同。

## 细节

- 绑定保存 `appId`、`appSecret` 与 `host`。App ID 是账号身份，密钥沿用全站掩码规则且永不回传，`host`
  则是唯一非机密的字段：留空即 `im.example.com`，且只接受裸主机名（带协议、路径或端口都会被拒，端口是平台自己的 8282）。
- 每次调用都把凭据放进查询串——事件 socket 上是 `?auth=<appId>.<appSecret>`，每个 HTTP 请求上是
  `?appid=…&secret=…`——因为平台没有 token 换取：没有签发、没有过期，服务端把自己构建的每条 URL 都当作
  机密，任何错误信息都不引用它。
- 一条 WebSocket 承载该机器人参与的全部会话。带顶层 `event_id` 的帧在被读取之前以
  `{"ack": "<event_id>"}` 应答，平台会重投未确认的帧，确认与去重因此各自处理重投。连接断开后按
  2、5、10、30、60 秒退避重连，此后一直用最后一档。
- 群消息与团队帖子只有带平台自身的 `at_me` 标记时才会交给智能体；单聊不设这道闸门。
- 被接受的消息会以推推自己的「收到」表情回执一次，且在运行开始之前；平台拒绝回执时只损失这个
  手势，绝不会被记为投递失败——不支持该手势的另外四个渠道也不会被问及。
- 出站方向，平台没有 reply-to 字段，一次回复就是发进同一个会话，已发出的文本也无法事后编辑。图片与文件
  都以同一个 `msgtype: "file"` 发出——平台没有独立的图片消息类型，这是已知的能力降级。团队帖子是唯一会渲染
  Markdown 的会话形态（若平台拒绝这次渲染，同一段文字会以纯文本重发而不是丢掉），但它不接受上传的附件。
- 入站方向，文本、图片与文件按普通输入送达；语音与视频不作为媒体下载，只以一行带 URL 的文本进入对话。
- 在 Session 仍处理上一条消息时到达的消息，会在该渠道的会话里收到一句「已排队」——每段忙碌只回一次，
  所有渠道一致——而不是让发送者一直静默等到答案。
- 凭据探测就是事件 socket 的握手，不发送任何内容，也不报出账号名。`POST …/messaging/tuitui/test-message`
  沿用共用的测试文本，并在推推里给机器人发过消息之前返回 409 `tuitui_no_chat`。
- Web 端的绑定编辑器在其余四个渠道旁新增了本渠道的表单。
