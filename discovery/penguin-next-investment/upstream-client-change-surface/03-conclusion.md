# ③ 结论与建议 · upstream-client-change-surface

## 结论（推荐 D1 + D2，D3 待确认）

- **D1（先做，零风险）**：精读本地 agenthub 0.4.11 的 OpenAI 系客户端（确认是否发亲和键、有无缓存选项），并**升级到 0.4.15**，随后重跑一段真实会话观察命中率。
  依据：U6、U7（请求形状修复最可能是前缀漂移的直接来源）、U2（升级在 semver 允许范围内）、U5（OpenAI 系无缓存字段工作 → 只能靠前缀稳定）。
- **D2（并行）**：产品侧**可见部分指纹**（对 messages 与系统提示做哈希，写入 Trace），不动上游即可判定"产品是否在 context 内改了前缀"。依据：U1（职责边界：上游管 wire，产品管自己看得见的部分）+ 子议题 1 方向 A。
- **D3（待确认后再做）**：在 agenthub 加 `prompt_cache_key`，或暴露"请求选项透传口"由产品侧决定。依据：U1（自有仓库可改）、U3；**前置条件**：确认所连网关是否支持该键。

## 建议（落地路径）

- **D1**：升 `packages/core/package.json` 的 `@prismshadow/agenthub` 到 `^0.4.15` → 重建 Web 产物（版本号会被烘进 bundle）→ 在 **7466 + 临时数据根**跑一段会话 → 对比升级前后的"整段未命中占比"。
- **D2**：在请求前计算可见部分指纹并落 Trace；与 D1 同一次实测里一起观察。
- **D3**：先向网关侧确认支持度（外部约束），确认后再定"上游加键"还是"透传口"。

## 待确认项

- 网关对 `prompt_cache_key`（或等价 sticky 机制）的支持度。
- 0.4.15 是否改变本产品的 wire 前缀（实测）。
- 升级是否引入回归（0.4.12–0.4.15 均触及工具结果/reasoning 形状 → 需跑测试与一次真实工具链会话）。

## 否决记录

| 被否方向 | 理由（依据） |
|---|---|
| fork / vendor agenthub 到产品仓库 | 上游是自有仓库、可正常发版（U1、U4），分叉维护成本无收益 |
| 一上来就改上游加 `prompt_cache_key` | 先要确认网关支持（未验证），且 D1 的请求形状修复可能已解决主要问题 |
| 把缓存策略写进产品核心 | 职责错位：wire 形状归上游，产品只应持有"可见部分"的判断 |
| 与 D1 无关地切换协议对照 | 先以最小改动（升级）取证，再谈协议层对照，避免同时动多个变量 |

## 声明

本流程**不执行任何改动**；D1 涉及版本升级、D2 涉及产品仓库改动，均需用户另行批准，并按既有规矩在 7466 + 临时数据根先验证。
