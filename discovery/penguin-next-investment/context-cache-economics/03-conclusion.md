# ③ 结论与建议 · context-cache-economics

## 结论（推荐 2 个方向）

**A. 请求前缀指纹审计（先做）**
在发请求前记录 `sha256(rendered prefix)` + 前缀长度 + 影响缓存的参数（thinking level、模型引用、工具集指纹），随 Trace 落盘。目的：一次记录即可区分两种根因——**产品在 context 内动了前缀**（违反事实 5 的自述不变量）还是**上游未保留/轮换了缓存**（事实 3 的"读到更旧快照"）。
依据：事实 3、4、5、6、7 + 侦察推论 3、4。

**B. 指标诚实性与成本口径（并行）**
把"整段未命中 0%"拆成**冷启动 0%** 与**热会话整段丢 0%**；在命中率旁显示"本轮重复处理的 input tokens 与折算成本"。
依据：事实 1、2、3 + OpenAI 官方"命中率下降仍可能更省"。

## 建议（每个方向一句话落地）

- **A**：在请求构造前挂一个指纹钩子（本仓库侧 `packages/core/src/llm/` 或经 `@prismshadow/agenthub` 暴露的请求选项），指纹写入该轮 Trace 记录。
- **B**：`usage_records` 聚合增加"是否冷启动/是否热丢失"的判定（依据该轮之前该 session 是否有成功写入），并在 `chat-page.tsx:1657` 处的呈现与两本 strings 里给出新文案。

## 待确认项（阻塞 A 的设计，不阻塞 A 的开工）

- `@prismshadow/agenthub@0.4.11`（事实 7）是否已经发送缓存亲和键，或暴露可传参的扩展点 —— **需一次源码精读**。若它已发键，则 A 的钩子位置与 B 的口径需要据此调整。

## 否决记录

| 被否方向 | 理由（依据） |
|---|---|
| 立刻发送 `prompt_cache_key` / 自研亲和调度 | 字段与支持度因网关而异，可能被忽略；且它只解释"多后端轮换"，对"必须完整匹配 unit"（侦察·DeepSeek）解释力更弱；业务视角也认为这是平台侧能力（见 ④） |
| 先砍上下文 / 更频繁 compaction | OpenAI 官方：更少 input tokens 即使命中率下降也可能更省钱 → 这是口径问题，先砍是拿体验换数字（事实 5 亦说明 strict 层前缀变更会破坏缓存） |
| 把缓存命中率当唯一北极星指标 | 模型间 43%–86% 差异大、混入冷启动（事实 2、10 号候选）；单看命中率会误导 |
