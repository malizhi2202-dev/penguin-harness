1产品全景

1.1 一句话定位

PenguinHarness 是开源、本地的多 Agent 应用自动开发平台：在你的电脑或服务器上运行， 自动串联 Agent 应用的创建、评测、优化与部署。README 里那句对照说得更直白—— 「使用 LangChain，以 1 倍速度人工构建 Agent；使用 PenguinHarness，以 100 倍速度用 Agent 构建 Agent」。

本地优先
数据在你自己手里
会话、轨迹、记忆、密钥全部落在本机数据根；服务端只监听回环。
Apache 2.0
开源协议

1.3 能力地图

对话与执行

  • 一次任务 = 多轮工具调用的 ReAct 循环，流式输出
  • 工具调用并发执行，审批模式可配（默认拒绝）
  • 上下文到阈值自动压缩并轮转，长任务不中断
  • 断线/限流自动重连阶梯，重发不重复计费

多 Agent 协作

  • Project → Agent → Session 三层隔离，各自独立记忆
  • 子 Agent（subagent）可派活并回收结果
  • Agent 模板：从公共配置复制，含提示词、技能与钩子

能力扩展

  • 内置工具集（文件、搜索、命令、网络、待办等）
  • MCP：接入外部工具服务器，失败不致命
  • 插件库：内置 12 个插件（技能与／或钩子包），按 Agent 安装启停
  • 技能：磁盘上的说明文档，按需进入上下文

可观测与成本

  • 轨迹：每个请求的完整事件流落盘，可回放续跑
  • 成本中心：按会话/模型/时间聚合 token 与费用
  • 前缀缓存命中：每条请求记录它发出的前缀指纹

对外通道

  • Web App（本服务端自带前端）、CLI、SDK
  • 消息通道：把会话接到 IM，入站消息变任务
  • HTTP API：前端与自动化共用同一套接口

部署形态

  • 桌面端应用（本机窗口）、penguin server（单进程服务）
  • npm 安装、在线安装脚本、Docker
  • 机器页：把当前这套安装推到 ~/.ssh/config 里的主机

1.4 这个产品不做什么（边界）

明确不做

  • 不做模型托管：不训练、不代管权重，只做调用与编排。
  • 不做云端账号体系：默认单机单账户（admin），成员与角色是这台服务端内的概念，不接外部 SSO。
  • 不替你保管别人的密钥：密钥按 Project 存在本机数据根，接口读取时一律打码。
  • 不做通用工作流引擎：编排单位是「Agent 的一个任务」，不是任意 DAG。

安全底线（贯穿全篇）

  • 服务端默认只监听 127.0.0.1；对外暴露由使用者自己选择（反代 / 端口转发）。
  • 工具执行默认拒绝：审批模式不配就等于不放行。
  • 命令类工具受策略与超时约束，输出有上限，进程可中断。
  • 预览类地址固定走 localhost 域名：127.0.0.1 被保留给工作区预览。

2核心概念

这一章把产品里的名词各指哪一件具体的事、彼此什么关系、落到磁盘上是什么，一次讲清。 后面架构、时序、界面三章都建立在这套对象模型上。术语与代码保持一致：口语里的「一句话」是 Task， 口语里的「一次回答」在代码里就是一个 Request。

2.1 四层对象模型

从粗到细是 Project → Agent → (Workspace) → Session → Task → Request。 前三层是配置与隔离的单位，后三层是执行的单位：一个会话里的所有执行都写进同一批轨迹文件。

层 是什么 关键属性 落在哪里
Project
项目		 组织 Agent 的顶层单位，并把模型表与凭据圈在项目内。多用户下用户与项目是多对多。 目录名即 id；成员按项目授权（owner / member） <数据根>/<项目>/.project_config.toml
Agent
智能体		 执行主体。它整个行为都是可编辑的文件，不是代码：系统提示、技能、钩子、记忆、默认模型与思考等级。 恰好一份持久状态目录，可服务多个工作区；可从公共配置的模板复制 <项目>/agents/<agent>/agent_state/
Workspace
工作区 		一次运行的工作目录，也是模型能看到的唯一文件范围。目录必须已存在，否则会被分配一个临时工作区。 持久工作区各有自己的记忆范围；临时工作区没有 <agent>/workspaces/tmp-<8hex>（临时）
Session
会话		 在一个（Agent, 工作区）下的一段连续对话。创建时即锁定模型与工作区，之后不再变。 id 形如 session-YYYY-MM-DD-HH-mm-ss-8hex；携带思考等级、实时 MCP 连接、转向与后台通知队列 <agent>/traces/<日期>/<session>_NNN.jsonl
Task
任务		 一次用户输入触发的执行目标，由一个或多个连续的请求组成。不再产生工具调用时结束；也可能被中断或触到大限。 结束边界上会运行停止钩子；同一会话同时只跑一个任务 轨迹里的一段事件区间
Request
请求 / 轮次 		对模型供应商的一次调用：上下文 + 工具定义进，流式输出出。它同时就是「一轮」（Turn），也是重试的最小单位。 只有完整送达的回答才提交进历史，因此失败可安全重发 轨迹里成对的 request_begin / request_end

隔离靠 Project 与 Agent，复用靠 Agent 模板，可观测靠「一个上下文 = 一个轨迹文件」，可重试靠「请求是不可分割的重发单位」。 另有两条容易混：轮次上限按任务计（max_turns），上下文轮次上限按上下文计（max_session_turns）。

2.2 执行模型（Task · Request）

一次任务在轨迹里就是一条事件流。下面是一次「让 Agent 执行 ls -la 之类命令再总结」的真实顺序， 关键在于两点：审批是串行的、执行是并发的；token_usage 与 request_end 不等工具跑完—— 晚到的工具输出会落在 request_end 之后。所以一次「轮次」的边界不等于工具执行的边界。

1
engine → trace
request_begin 请求开始，并记录本次发出的前缀指纹（见 2.3）
2
provider → 界面
partial_thinking → thinking，partial_text → text（增量只给界面，完整消息进轨迹）
3
engine
partial_tool_call → tool_call 调用 A 完整到达 → approval_decision(allow) → 派发执行；调用 B 同样流程。审批按流顺序逐个来，执行并发
4
environment → 界面 + trace
partial_tool_call_output → tool_call_output，按完成顺序产出（例子里 B 先跑完）
5
engine → trace
token_usage（本次请求的 token 与缓存读写，成本中心的数据源）→ request_end(completed)
6
environment
A 的输出晚到：在 request_end 之后才补上 partial_tool_call_output / tool_call_output
7
engine
A、B 都收齐后，按原始调用顺序重排再发下一次 request_begin；若本轮没有工具调用，任务到此结束

提交与重发

供应商的历史只在回答完整送达并通过校验后才追加。所以流被截断、负载解析失败、请求被拒——这些异常都不会污染历史： 引擎可以把同一份输入原样重发，并追加一个 [turn_retried] 块，让模型从已经产出的部分接着做，工具不会重跑。 用户主动中断则打的是另一个标记 [turn_aborted]。

被切断时留下的「carry-over」

运行被中断（用户中止、触到轮次上限、重试阶梯用尽）时，没送出去的输入不会丢：已提交的工具结果按结构化输出重发， 没跑完的调用补一条 [interrupted: tool aborted by user] 占位以保住配对；模型输出不完整时，整轮被压成一条 [turn_aborted] 文本。这部分内容只进模型上下文，从不写轨迹。

事件清单（协议即文档）

上下文元信息
session_meta（每个上下文恰好一条：会话 id、供应商、模型、窗口、装配好的系统提示、Agent 状态目录、工作区）
完整消息（进上下文）
text · thinking · inline_thinking · tool_call · tool_call_output · image_url · inline_data
运行事件（在上下文之外）
tool_list_ready · mcp_connect_begin · mcp_connect_end · request_begin · request_end · approval_decision · token_usage · compaction_begin · compaction_end · abort · subagent · hook
流式增量（仅界面）
partial_text · partial_thinking · partial_tool_call · partial_tool_call_output（start → delta* → stop，拼起来等于那条完整消息）

轨迹只记三类：session_meta、完整 model_msg、全部 event_msg。 不记流式增量；子 Agent 的消息不写进父会话轨迹（只留一条 subagent 指针事件）。

2.3 上下文与三层严格度

一个模型上下文 = 一个活的模型连接 + 它固定的请求前缀（系统提示、工具集含 MCP、模型引用）+ 恰好一个轨迹文件。 ContextEngine 是同一时刻只持有一个上下文的 ReAct 循环，只按 OmniMessage 说话。 上下文在会话第一次运行时打开（装配好的一切写进 session_meta），在每次压缩完成时关闭并轮转。

层级 包含什么 改动的代价 何时生效
严格层 系统提示、工具集（含 MCP 条目）、模型引用 请求前缀变化 → 供应商的提示缓存整份失效，下一个请求按全价重算输入 只在上下文打开（或轮转）时装配，运行中改了也是下次轮转才生效
不进上下文 密钥保管库、工具的读写权限、项目命令策略 无（从不进入请求），但它们与严格层同一次轮转重读 下次上下文轮转
软限制层 思考等级（thinking level） 前缀没变，但供应商侧缓存的上下文会失效（该参数进入请求参数） 会话内随时可调，从下一个请求起按请求携带
不受限 审批模式、压缩设置（阈值 / 模式 / 摘要提示） 无：审批模式不进入请求；压缩设置在每次检查点按文件修改时间重读 立即

思考等级共六档：none · low · medium · high · xhigh · max（子 Agent 不用 none）。 它不写进轨迹——这正是前缀指纹要额外携带它的原因。

压缩（Compaction）

什么时候触发

  • 按上下文：上一次请求的总输入 token 达到阈值（默认 256k，实际取它与「模型窗口 − 2048」的较小值）。
  • 按轮次：上下文内请求数达到上限（默认不限）。
  • 手动：界面上的压缩按钮或会话接口。

检查点在每个产出 token_usage 的请求之后，所以压缩可能在任务中途发生；此时本轮工具输出都已配对收齐。

怎么做

  • 摘要请求追加到旧上下文上发出，工具集保持逐字节不变——这是为了不打断供应商的缓存。
  • 取出摘要后包成一条 [context_summary] 用户消息，在新的模型上下文里继续。
  • 另有一种 丢弃模式：不摘要，直接开新上下文。
  • 压缩失败或被打断：原上下文与轨迹索引都保留，不会退化成丢弃。

压缩后，[context_summary] 那段文本就是此前对话的唯一记录（系统提示也会这样告诉模型）； 任务边界上的摘要会与下一个用户输入合并成新上下文的第一条输入，任务中途的压缩则直接把摘要作为新上下文的第一条输入。

前缀指纹：把「缓存为什么没命中」变成可查的事实

供应商缓存的是渲染后的前缀，前缀一变就整份不命中；而 token_usage 里两种完全相反的原因长得一模一样 （cache_read 为 0、cache_write 等于整份输入）：可能是我们自己改了前缀（严格层被破坏）， 也可能是供应商不再提供缓存（过期、驱逐、路由）。所以每个请求都会在 request_begin 上记录前缀指纹： 整份前缀的哈希、仅固定头部的哈希（系统提示 + 工具清单）、记录条数、序列化长度、是否逐字节扩展上一次、 以及本次携带的思考等级。同一上下文内头部哈希不变 + 逐字节扩展为真，说明前缀没动过——此时若仍不命中，账就该记在供应商那边。

2.4 工具与审批

刻意精简的工具集（7 个）

命令
exec_command · input_command
文件
read_file · edit_file · write_file
子 Agent
run_subagent · input_subagent

没有单独的「搜索」「网页抓取」「待办」工具：检索用命令跑（rg/grep）， 网页抓取这类能力由插件以技能形式提供，计划性交给模型自己组织。这正是「更少工具调用、更少 token」的来源。

执行契约

  • 工具只产增量输出，由执行环境统一收尾：加框、绑定 tool_call_id、合并超时、超长输出掐头留尾截断。
  • 配对：每个提交的 tool_call 恰好对应一条 tool_call_output（被拒也有合成输出）。
  • 并发：审批串行、执行并发，输出按完成顺序到流上，发给模型前按原始调用顺序重排。
  • 自定义工具集：配置里写了就整体替换默认工具集，不写则保留默认。

审批

模式 行为 典型用途
全部放行 allow-all 每个工具自动通过 无人值守、可信工作区
全部拒绝 deny-all 每个工具自动回绝 只想让它读上下文、别动手
放行只读 read-only 只读类工具自动通过，其余转人工 推荐默认：能查不能改
总是询问 always-ask 每个调用都转人工 敏感仓库、逐条确认

服务端在每次决策时重读审批模式，所以改完立刻生效。执行前的钩子（pre-tool-use）先于审批被咨询： 它说拒绝就直接拒、说通过就不再问人，而项目命令策略始终压过钩子——策略否决不是一个「审批答复」，而是配置层面的红线。 被拒的调用会得到一条合成的 aborted 输出（「Tool call denied by user.」/「…by policy.」），模型能看到自己被拦了。

MCP（外部工具服务器）

  • 三种传输：stdio（命令 + 参数）、http（流式 HTTP）、sse（旧协议，必须显式声明）。
  • 懒连接：创建会话立刻返回；第一次运行时并行连上所有服务器并发现工具，用 mcp_connect_begin / mcp_connect_end 包起来，随后是 tool_list_ready。
  • 结果成为该上下文的快照（服务器端的工具增删在本次上下文内不生效，下次轮转重连时才更新）。
  • 工具以 mcp__<服务器>__<工具> 加入同一个命名空间，走同样的审批与执行契约。
  • 失败不致命：连不上或配置非法的服务器只在日志里警告并跳过，会话照常跑。

绑定的四条规则

  1. 一个会话 × 一个通道 = 一条绑定。多条可以并存保存，但同时只允许启用一条；某个通道账号已被别的会话启用时，切换会被拒并提示冲突。
  2. 一条绑定只服务一个对话：记住第一次跟它说话的那个聊天，其他来源的消息被静默忽略——这是把一个机器人接到一个会话的边界。
  3. 会话正在跑任务时，新消息不是另起任务，而是按转向（steering）或排队进入正在跑的这轮。
  4. 推推的地址与凭据：凭据写在每个请求的 URL 里，因此那条 URL 本身就是密钥；服务地址是必填项且只填主机名（端口固定），缺失会被明确拒绝。产品不再替你猜一个默认域名。
文档中的凭据一律为示意值

3.1 进程与拓扑

产品只有一个常驻进程：它同时提供 HTTP API 与内置前端。引擎、工具执行、轨迹写入都在这个进程里； 数据落在本机数据根，不经过任何外部服务（模型调用除外）。

浏览器 / 桌面窗口 —HTTP + SSE→ PenguinHarness 服务端进程 —HTTPS→ 模型供应商
同一进程内： HTTP 路由 / SSE ContextEngine（任务循环） 工具执行环境 轨迹写入
落盘： SQLite web.db（用户/会话索引/用量/绑定） 轨迹 JSONL（逐会话） 项目配置 TOML（模型与密钥）

形态 怎么起 端口 / 数据根 用途

锁文件是 <数据根>/server.lock，里面记着 pid 与端口；判定「有人占着」要两个条件同时成立—— 进程还活着且那个端口还在接受连接，否则视为过期锁、直接覆盖。锁按数据根而不是端口持有， 所以「换个端口再起一个」并不能绕过它；开发后端与安装版分端口、开发 CLI 再分一个端口，都是为了避免代理静默连到另一个实例。 被占时的退出码是 3。

一次启动按顺序做这些事

  1. 读环境变量、装出网代理（这是它唯一的出网非模型请求通道）
  2. 读配置（端口、数据根、预览来源等）
  3. 独占检查：数据根已被活着的实例占用则退出（码 3）
  4. 加载扩展（extensions.json）
  5. 打开数据库、启动运行时核心（热更新平台会在这里把业务面装配起来）
  6. 应用持久化过的代理设置 → 构建 HTTP 路由 → 播种管理员账号 → 监听端口 → 装进程信号处理器

core 内部的分层

engine

任务循环本体：一轮的推进、工具审批与并发执行、中断与 carry-over、上下文压缩与轮转、轨迹写入时机。

llm

供应商流量的唯一出口：把 OmniMessage 转成供应商请求、把流式响应转回事件、算 token 与缓存计数、判定重试。

environment

工具实现与执行环境：文件、检索、命令、网络、待办、子 Agent，以及 MCP 客户端。

trace

轨迹的读写：追加事件、按上下文轮转文件、回放一段历史以恢复现场。

omnimessage

唯一消息协议：信封 + 载荷、全部 builder、标记块（steering、retried、transcript 等）。

state

文件状态层，也是磁盘布局的唯一权威：数据根里每个路径都定义在 state/paths.ts 一处；项目配置、Agent 状态、记忆、技能安装、模型目录都在这里。

hooks

循环的三个钩子点（停止 / 工具使用前 / 用户输入），把插件里的钩子包作为子进程运行。

interfaces

对外的稳定契约：LLM 与执行环境两个接口，以及共享类型。「人的界面」不是类，而是一次会话运行本身。

internal

共享基础设施：端口常量、服务生命周期（含「重启以更新」的退出码）、原子写、命令策略。

产品不自己实现供应商客户端：所有模型流量经内部的 LLM 适配层转交给外部依赖 @prismshadow/agenthub， 协议差异（Chat / Responses / Messages 等）在那里收口，产品只为它准备请求形状。

4核心时序

这一章只讲六件事怎么发生：一次带工具的请求、断线重连、压缩、重启恢复、外部消息进来、新上下文装配。 每条都按真实代码路径写，并标出「用户能看到什么」。

4.1 一次请求：审批串行、执行并发、输出会晚到

1
会话入口
输入先进轨迹，再发请求。第一次运行时，上下文的开场记录（MCP 连接探测、工具清单）写在输入之后——它们在流上早就实时给过界面了。
2
组装本次输入
顺序是：上一轮留下的摘要（如果有）+ 上次被切断的 carry-over + 本次用户输入；随后清空排队中的后台通知与转向消息。
3
发请求
写 request_begin（带前缀指纹）→ 交给模型层。入参里角色混杂或为空会直接判 invalid_input，不浪费一次网络往返。
4
流式回流
增量给界面；完整消息进轨迹。每个工具调用一完整到达就立刻审批（先问执行前钩子，再问审批），决策本身也写成一条事件。
5
批准后立刻派发
工具执行是发射即忘：它和「继续消费模型流」「审批下一个调用」并行跑，所以 A 可能比 B 晚完成。
6
收尾
模型的流一结束就记 token_usage 与 request_end，不等工具跑完。跑完的输出以完成顺序追加，界面上看起来是「请求已结束、工具卡还在转」。
7
下一轮
所有调用收齐后按原始调用顺序重排（按 tool_call_id 配对、去重）作为下一轮输入；没有工具调用且没有新消息，任务结束。

被拒绝的调用不会消失

它得到一条合成的 aborted 输出，内容是一句固定说明：用户拒绝 / 策略拒绝 / 某个钩子拒绝（附原因）。 这样「有调用必有输出」的配对契约在任何分支下都成立。

子 Agent 的输出只给界面

带子会话标记的消息会转发到流上，但不写进父会话轨迹；父会话只留一条指针事件，记录子是哪个会话。 轨迹浏览时展开这条指针，就能看到子会话自己的完整记录。

4.2 断线重连：分类在模型层，重试在引擎

谁负责判断「能不能重试」：模型适配层。它从不把异常抛给引擎，而是先按下面的规则给出一个状态与错误码， 并且保证流被正确收尾（把 start → delta → stop 补完），因此界面不会留下半条消息。

出了什么事 判定 错误码 为什么
用户主动中止 aborted user_abort 人的意图，走 carry-over 而不是重试
超时 retryable timeout 换一次可能就好了
JSON 解析失败、工具参数解析失败、空响应、流被整齐截断 retryable malformed 供应商侧抖动，重发通常能恢复

供应商 4xx 拒绝（408 / 429 除外） fatal rejected 请求本身不该被发出去

4.3 压缩：先摘要，再换上下文

何时触发

  • 按输入量：上一次请求的总输入达到阈值。默认 256k，实际取「配置值与模型窗口 − 2048 的较小值」；窗口未知时按 128k 估算。
  • 按轮次：上下文内请求数到上限（默认不限）。
  • 手动：界面或接口发起。

检查点在每个产出了用量数据的请求之后，所以压缩可能在任务中途发生；设置每次都在检查点按文件状态重读，改完立即影响下一次判断。

两种收尾

  • 任务边界：摘要先存起来，等下一个用户输入一起成为新上下文的第一条输入。
  • 任务中途：本轮工具输出先折进压缩请求，摘要取出后直接成为新上下文的第一条输入，随后才是排队的通知与转向消息。
  • 丢弃模式：不发任何请求，等到真正的任务边界再换上下文，下一轮输入原样使用。

摘要请求的三条纪律

  1. 压缩提示追加在旧上下文上发出，工具集逐字节不变——这是为了不打断供应商的提示缓存。
  2. 合格的摘要必须非空且没有工具调用；如果模型反而调了工具，会补一条合成的工具错误输出再重试（附一句额外引导），不会把半成品当摘要。
  3. 预算用尽就放弃压缩：原上下文与轨迹索引都保留，绝不退化成丢弃。失败会写进错误表（码 compaction_failed）。
阶段 事件 界面
开始 compaction_begin{reason, mode, context, turns} 出现一行提示：摘要模式显示「压缩中」，丢弃模式显示「清理中」
进行中 摘要请求的思考与正文按普通流式消息走 那行提示可以展开，看到思考与结果两段，各自计时
结束 compaction_end{reason, mode, status, attempt?, error_code?, error_message?} 变成「已压缩」/「已清理」；失败则显示原因并丢掉写了一半的草稿

换上下文的动作

  • 开场记录（MCP 连接探测、工具清单）边产出边给界面，然后再装新的模型连接。
  • 轨迹文件轮转是延迟的：旧文件原样不动，索引在下一次真的要写时才 +1，所以「压缩完没有后续消息」不会产生空文件。
  • 新文件以 session_meta（新的系统提示与固定事实）开头，紧接这次上下文的开场记录。
  • 如果新上下文装配时就失败，旧上下文继续当家，不产生轮转。

4.4 重启后恢复：轨迹是唯一真相

1
定位
找序号最大的轨迹分片（跨日期目录），用容错读法读：最后一行被截断就当没写（静默容忍），中间行损坏则跳过并留一条日志。
2
前置校验
缺 session_meta 直接报错；当初的工作区必须还在、模型必须还在项目配置里，否则报错而不是猜一个替代品。
3
重放
只重放已提交的轮次（request_end.status === "completed"），并保持工具调用与输出的配对。任何其他状态的整轮都被丢掉：那一轮的原始输入回到待处理区，等下一次运行再发。
4
补齐与丢弃
有调用无输出的，补一条「进程在工具跑完前退出了」的占位输出；没有对应调用、或已被回答过的孤儿输出，丢弃。计数从最后一条用量事件恢复。
5
给模型 / 给界面
给模型的是合并后的历史（相邻同角色会合并成一条）；给界面的是另一个来源——消息接口会把所有分片按序拼起来，并把子会话指针就地展开成子会话的轨迹。
6
续写
继续写在原来那个文件里。轨迹写入始终是「尽力而为」：写失败只警告，不影响任务。

上次正好停在压缩中间

如果最后一条是已完成的压缩，说明上下文已经关闭：恢复成空历史，并在需要时用最后一条已完成请求里的助手文本重建那份摘要。 如果只有一个「压缩开始」没有结束（进程死在请求中途），恢复时会先补写一条状态为可重试的结束事件，写了一半的摘要直接丢弃、不重建。

为什么这套能自洽

因为「提交」与「轮转」都落在同一个只追加文件里，且都有明确的机械标准； 数据库只存索引，所以即使数据库丢了，轨迹也能重建出会话的全部内容与现场。

4.5 外部消息进来（以推推为例）

1
绑定与连接
读那条「已启用」的绑定（凭据与服务地址三项都必须齐全，缺一项就明确报配置畸形），由通道连接器建立长连接；连上→状态已连接，出错→状态错误并记一条连接失败。
2
通道侧门禁
推推会把所有群消息推过来，所以没有「@我」标记的群消息在连接器里就被丢掉（不留痕迹）；私聊不做这个限制。
3
归一化 + 去重
统一成 {对话、消息、文本、图片、文件}；消息 id 按「会话 + 通道」建索引，连接时还会用绑定里记的上一条消息 id 播种，所以重启也不会重复处理。重复投递是彻底的空操作——在任何回复之前就返回。
4
对话锁
只有第一次跟它说话的那个对话被记住，其他来源静默忽略。要换对话，就删掉绑定重建。
5
变成任务
文本直接作为用户输入交给会话——与你在界面里手打完全一样，不加任何来源标记（产品刻意不让模型知道消息从哪来）；图片作为图片输入；文件落到会话暂存目录并以一行「已附加文件」告知；什么也解析不出则回一句双语提示。
6
会话正忙
不当成新任务插队，而是进队列（界面显示排队条数），会话空下来自动接着跑；同一段忙碌期间只提示一次「已排队」。消息水位最后才写——所以宁可重投一次，也不静默吞掉消息。
7
回执
挂在会话的输出通道上：忽略子 Agent 的消息、跳过压缩摘要，只转发完整的助手文本；按完成顺序排队发送；开了「只发最终回复」就只保留最后一条，在会话空下来的那一刻发出；审批请求会另行插一条通知，不被「只发最终回复」挡住。发送失败记录到绑定上，界面上能在绑定状态里看到。

桥接是服务端运行时组件，与会话调度器一起启动：服务端不在跑，就没有入站处理、没有回复、也没有连接。

4.6 新上下文装配了什么

上下文打开时（会话第一次运行、或每次压缩轮转），从磁盘重新读一遍下列内容：

打开时重新读 会话创建时就固定、不再重读
Agent 状态（系统配置与 AGENTS.md）、密钥保管库、项目配置（含命令策略）、 已安装技能、定时任务名单、记忆范围与索引 会话 id、工作区、模型条目与凭据、思考等级固定值、子 Agent 深度、来源（是人开的还是定时任务/子 Agent 开的）

系统提示的装配与「只注入元数据」

  • 占位符按固定顺序替换：AGENTS.md 正文、保管库键名、技能元数据、Agent id、项目目录、会话 id、当前目录、供应商、模型 id、平台、系统版本、Shell、日期；最后一次性替换记忆索引、保管库、技能、定时任务四块——一次性替换意味着这些内容里再写占位符也不会被二次展开。
  • 注入的只有元数据：保管库只给键名（值在执行工具的子进程里），技能只给名字与一句话说明，记忆只给索引，定时任务只给名字。
  • 模板里没有 Shell 占位符、且当前 Shell 不是 bash 时，会补一行 Shell 说明。

工具清单会被裁剪

按模型能力筛（不支持视觉的模型不拿图片相关能力），按子 Agent 深度筛（到达最大深度的会话失去派发子 Agent 的两个工具，避免无限套娃）。 自定义工具集在配置里写了就整体替换默认清单。

开场三步

1
探测
若有待连接的 MCP 服务器，先写一条「连接开始」
2
连接与发现
并行连上所有服务器并取回工具清单，写「连接结束」（含每个服务器的结果）
3
固定
写「工具清单就绪」，然后用这份清单装配模型连接——此后本上下文的请求前缀不再变化
改配置什么时候生效？

模型连接在构造时就冻结了工具集、系统提示、输出上限与快速模式，之后每次请求只允许覆盖思考等级与由窗口推导的输出上限。 因此对系统提示、技能、记忆、MCP 配置、密钥的修改，都要等下一次上下文打开（压缩轮转或新建会话）才生效； 而审批模式每次决策都重读、压缩设置每次检查点都重读，所以改完立刻有效。这不是实现细节，而是「前缀不变 → 缓存命中」这条主线的一部分。

5使用指南

这一章按模块写操作手册：每个模块讲清你会看到什么、怎么用、有什么讲究。 侧栏的顺序就是模块顺序：对话 · 智能体 · 插件库 · 模型库 · 机器 · 成本中心 · 轨迹观测 · 评估中心。

5.1 第一次打开

  1. 起服务端：penguin server（默认端口 7364，只监听本机回环）。首次启动会自动建好管理员账号， 并把一个首次登录链接打印在终端里——密码是随机生成、直接丢弃的，所以必须用这个链接进去自己设一个， 或者启动前用环境变量指定初始密码。
  2. 认领：打开链接即设置新密码并登录。首次认领会给浏览器种下登录凭据，之后 30 天内免登录（有滑动续期）。 注意这是一个 GET 链接，可能被邮件客户端预取，所以它不是一次性的。
  3. 建项目：项目是模型密钥与 Agent 的边界。默认会有一个项目可用；多项目适合隔离「不同客户 / 不同环境 / 不同密钥」。
  4. 配一个模型：进模型库，至少配一个「供应商 + 模型 id + 密钥」，并把它设为默认（还可以单独指定视觉模型）。 密钥写入项目的配置文件，接口回读时一律打码。
  5. 建 Agent（可选）：默认 Agent 已经能用。想定制系统提示、技能、钩子时再新建一个； 新建时可以从公共配置里的模板复制起步。
  6. 开对话：从「新对话」开始。第一次发消息时，产品才真正去装配上下文（连 MCP、装工具清单），所以第一条消息会稍慢一点，之后同一会话内就没有这个开销了。
关于「换端口再起一个」

一个数据根同一时刻只允许一个服务端（被占用时进程以码 3 退出）。想在别处试跑，请同时换端口和数据根， 否则会被锁挡住，或让前端代理连到另一个实例上。

5.2 对话

你会看到什么

  • 思考与正文流式出现；思考块可折叠。
  • 每次工具调用是一张可展开的卡片，含参数与输出；需要审批的调用会停在「待审批」。
  • 会话状态会显示「运行中」「压缩中」「运行完毕，未读」等。
  • 成本与用量按会话累计，顶部能看到本会话的用量概览。

能做什么

  • 发消息 / 排队：任务跑着时再发，会按「转向」在下一个输入组装点并进去，而不是另起一个任务。
  • 中止：随时停；被切断的输入不会丢，下次运行会接着做。
  • 立刻重试：断线等待期间可以跳过倒计时，立刻重发。
  • 手动压缩：上下文要满时提前压缩。
  • 目标模式：给一个目标与轮次预算，由停止钩子在每轮任务结束后决定是否再来一轮。

四种审批模式

界面上的名字 内部值 什么时候用
全部放行 allow-all 无人值守、可信工作区、批量改造
全部拒绝 deny-all 只想让它读上下文、不想让它动手
放行只读 read-only 推荐默认：查得动、改不了
总是询问 always-ask 敏感仓库、逐条确认

审批模式改完立刻生效（每次决策都重读）。但要注意：审批只决定「工具能不能跑」， 项目里的命令策略是更高的红线，钩子说通过也不能越过它。

思考等级与「先压缩再改」

思考等级有六档（none / low / medium / high / xhigh / max）。它是一个按请求携带的参数： 改了立刻对下一个请求生效，但会让供应商侧缓存的上下文失效——所以界面上会建议先压缩再调， 这样代价落在本来就要重建的那一次上。

看不到的三种「输入的来源」

转向
你在任务运行中发的消息，会在下一个组装点作为一段明确标注的用户消息插进去。
后台任务通知
后台命令或子 Agent 跑完时，由产品自己注入一条通知（带任务号与状态，附上还没给过的输出尾巴），你不需要去查。
外部消息
从 IM 通道进来的消息，和你在输入框里打进去的完全一样——产品刻意不给它加来源标记。

5.3 会话与工作区

  • 会话列表按 Agent 组织，可以按项目/时间筛选，能看到每条会话用的模型、工作区、最后活跃时间与是否已归档。
  • 分组与置顶：会话可以按分组折叠、把常用分组置顶；未分组的新会话会落到「最近一次对话」的语境里。
  • 归档：归档不等于删除。历史仍在磁盘上，可以随时找回并继续。
  • 分叉：从某个会话分出一支继续跑，原会话不受影响（分叉次数会记在会话上）。
  • 工作区：一个会话创建时就锁定工作区与模型，之后不能换。工作区必须是一个真实存在的目录； 没有指定时产品会分配一个临时工作区——注意临时工作区没有属于自己的记忆范围。
  • 子 Agent：派发出来的子会话有自己的轨迹，父会话里只留一条指针，展开即可查看。

  • 视觉模型：处理图片时用它。

界面上会给出「缓存命中率」。请把它读成命中占（命中 + 新写入）的比例：它是「同一批内容有没有被复用」的指标， 不是账单折扣。命中率低有两种完全相反的原因——我们自己改了请求前缀（系统提示、工具、MCP、模型引用变动）， 或供应商没给缓存（过期、驱逐、路由）。每个请求在开始事件上都记了前缀指纹，前者可以去轨迹里对照确认。

能怎么切

按时间范围、按粒度（小时/天）、按维度（日期 / Agent / 模型 / 会话）分组；模型维度总是「供应商 + 模型 id」成对出现，避免同名模型混淆。

错误表

同一页还有一张错误表，记服务端侧的失败（含来源、类型、状态码、截断后的消息）， 并标出这次失败会不会自动重试——正好对应 4.2 的阶梯：可重试的会等下一次，致命的不会。

5.9 轨迹观测

轨迹视图

  • 按事件逐条列出：请求开始/结束、审批决策、用量、工具调用与输出、压缩起止、钩子、子 Agent 指针。
  • 每条都能展开看原始载荷；一个上下文一个文件，压缩后的分片按序号续接。
  • 上下文构成：能看到这次发出去的系统提示、工具清单与历史规模。

用它回答的问题

  • 「这次为什么慢」→ 看请求耗时与工具耗时。
  • 「缓存为什么没命中」→ 对比相邻请求的前缀指纹是否继续扩展。
  • 「它当时看到了什么」→ 看该上下文的系统提示与工具清单快照。
  • 「子 Agent 干了什么」→ 展开指针事件。

轨迹是只追加、不修改的：崩溃最多让最后一行残缺，恢复时会容忍它。 因此它既是审计记录，也是恢复现场的唯一依据。

绑定这一步的规矩

  1. 一个会话对每个通道可以各存一条配置，但同时只能启用一条；同一个通道账号如果已被别的会话启用，切换会被拒绝。
  2. 一条绑定只服务第一个跟它说话的对话，其他对话的消息会被静默忽略——要换服务对象就删掉绑定重建。
  3. 启用后界面会显示连接状态与最近一次入站时间、最近一次投递错误、最近一次连接错误，方便排查。
  4. 会话跑着任务时，进来的消息会排队（界面显示排队条数），并在同一段忙碌里只提示一次。
  5. 推推：App ID 与 Secret 之外，服务地址是必填的，且只填主机名——协议头、路径或显式端口都会被拒（端口是平台固定的）。 另外凭据是写在请求地址里的，所以那条地址本身要当密钥看待。

「只发最终回复」打开后，中间过程不会一直往聊天里刷，只在会话空下来的那一刻发最后一条正文；但审批请求会另外插一条通知， 不会被这个开关挡住。子 Agent 的消息与压缩摘要从不外发。

7角色权限矩阵

7.1 两条正交的权限轴

权限不是「一个角色一把钥匙」，而是两个互相独立的维度：是不是管理员（用户级标志）与 在这个项目里是所有者还是成员（项目级关系）。管理员不是「超级项目成员」，而是多了一把服务器级的钥匙： 用户、服务器设置、机器管理与自助升级。

项目角色

所有者（创建项目的人）与成员（被加入的人）。项目里的写操作大多要求所有者。

管理员

用户标志，逐处在路由上检查；它同时是公共配置的唯一使用者（见 7.5）。

7.2 判定规则：先 404，再 403

  1. 项目所有者的判定只有一处实现：项目记录里的所有者匹配 → 所有者；否则查成员表 → 成员；都没有 → 无权限。
  2. 无权限时返回 404「不存在」而不是 403——这样别人无法通过错误码试探某个项目是否存在。
  3. 只有「确定存在、但你不是所有者」时才返回 403「需要所有者」。
  4. 这是唯一一处实现，所以新增接口只要走这套判断，就不会出现「某个接口忘了鉴权」的孤岛。

7.4 凭据、登录与限流

本机令牌

  • 数据根里的令牌是 32 字节随机串，权限 0600，每次启动重新签发。
  • 用它调用接口等同于内置管理员身份（包括事件流）。
  • 错误的令牌直接 401，不会退回用 Cookie 认证；比较是定长时间的。
  • 给 Agent 跑命令的子进程也会拿到它——所以「能读数据根」在设计上就等于「是本机管理员」。

浏览器会话

  • Cookie 是 HttpOnly、SameSite=Lax，30 天有效，并做滑动续期。
  • 真正的过期时间存在服务端记录里，Cookie 自身不是权威。
  • 只有显式开启「信任代理」且代理声明的协议是 https 时才加 Secure 标记。
  • 没有开放注册：管理员之外的用户一律由管理员创建。

7.5 两个特例

公共配置

它是一个保留的「伪项目」：对管理员来说等价于自己拥有的项目，对其他人则是「不存在」。 正因为复用了同一套项目权限判断，它的写接口不需要第二条规则就天然只有管理员能用； 界面上的三个全局配置项（模型库 / 智能体 / 插件库）就是这个范围。

桌面端单用户模式

桌面端把多用户面整个关掉：用户管理、成员管理等接口返回「仅多用户可用」， 初始密码提示条也不显示。同一份代码、同一套路由，只是运行形态不同。

公共配置 Common 项目之外的保留范围：公共模型表、Agent 模板、默认插件集 对非管理员表现为「不存在」；模板复制不带记忆、密钥、定时任务

9常见问题

为什么第一条消息明显更慢？

因为上下文是在第一次运行时才装配的：读 Agent 状态、连 MCP 服务器、发现工具清单，然后才发第一个请求。同一会话内不再重复这些开销（压缩轮转时会再来一次）。

缓存命中率不高，是我们改坏了还是供应商的问题？

去轨迹里对比相邻请求的前缀指纹：同一上下文内头部哈希不变且逐字节扩展，说明前缀没被动过，那么不命中就来自供应商侧的缓存过期或驱逐； 如果头部哈希变了，或者不再是「扩展上一份」，那就是我们自己动了严格层（系统提示、工具、MCP、模型引用）。

我改了系统提示 / 加了技能，为什么这次对话里没反应？

这些属于严格层：改动只在下一次上下文打开时生效，也就是压缩轮转之后或新建会话。压缩设置与审批模式是例外，改完立即生效。

调整思考等级为什么提示我「先压缩」？

因为它是一个按请求携带的参数：改了立刻生效，但会让供应商缓存的那段上下文失效。先压缩，等于把这个代价放在本来就要重建的那一次上。

换个端口为什么起不来？

因为单实例锁按数据根持有，不按端口。要并行跑一份，请同时换端口和数据根；被占用时进程以退出码 3 结束。

为什么用 127.0.0.1 打开界面会出问题？

那个主机名被保留给工作区预览（预览必须是另一个来源）。访问界面请用 localhost。

忘记管理员密码了怎么办？

停掉服务后执行 penguin server reset-admin-password，会得到一个可用的新初始密码。

任务被中断、或服务端崩了，会不会白跑？

不会丢：已提交的轮次留在轨迹里，未提交的整轮被退回成待处理输入，工具输出缺失时会补一条占位输出以保住配对。 恢复只重放已提交的轮次，因此不会重复执行工具。

消息平台重复推送同一条消息，会不会跑两次任务？

不会。入站先去重（并把上一条消息 id 记在绑定上，重启也不忘），重复投递是彻底的空操作；而水位是在工作做完之后才写的——宁可重投，也不静默吞消息。

为什么界面里找不到「技能」「定时任务」「轨迹」这些页面？

它们不是页面：技能 / 定时任务 / 记忆 / 密钥 / 钩子是智能体配置的标签页；轨迹观测是对话页的停靠面板；远程控制是面板兼弹窗。

机器页面在哪？

已经实现但尚未发布，侧栏不渲染入口。

文档说内置工具 9 个，实际是几个？

以代码为准是 7 个：命令 2 个、文件 3 个、子 Agent 2 个。这类已知差异集中列在附录 E。

定时任务为什么显示「已错过」？

因为该触发的时候服务端不在跑。定时任务是服务端组件：服务端停着，既不会触发也不会回复消息通道。

附录 E · 文档与代码的已知不一致

写这份文档时逐条比对过源码与仓库里的说明文档，以下差异以代码为准：

  1. 结束状态的取值：代码里是四种（completed / aborted / retryable / fatal），并另有一个错误码字段承载更细的原因 （超时、网络、解析失败、鉴权、被拒、参数不支持、输入非法等）；旧的六种说法（含 failed / timeout / malformed）只存在于文档里。
  2. 内置工具数量：架构文档写 9 个，注册表里是 7 个。
  3. 轨迹示例的顺序：说明文档的示例把 request_end 画在 token_usage 之前，代码是先记用量再记结束； 示例里给上下文元信息画的工具字段实际不存在——工具清单单独有一条事件。
  4. 文档里的一句话与实现范围不符：工具文档里出现的失败状态名在实现中已经是 fatal。

本产品对「文档与代码不一致」的态度是：把差异列出来，而不是让读者自己猜。改动其中任何一条时，请同时更新这里。
